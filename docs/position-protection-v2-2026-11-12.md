# 仓位保护重设计（v2）

日期：2026-11-12
范围：`backend/app/protection/`（v1 `engine.py` 保留为回滚路径）

---

## 1. 为什么不是继续打补丁

v1 的问题不是参数没调好，是四层结构叠在一起后互相干扰：

| # | 结构性问题 | 具体表现 |
|---|---|---|
| 1 | **状态是一坨 JSON 全量读写** | `_load_state()` 每轮读整表、`set_value` 整键覆盖。44 个协程各读各写，跨币种丢更新：A 币刚标记 T1 已执行，被 B 币用旧副本写回，下一轮 T1 再来一次。 |
| 2 | **仓位身份靠猜** | 用 `openTime` / `entryPrice` 变化判断「是不是新仓位」。交易所把减仓后的均价重算写回，就被判成新仓 → 风险周期重建 → 按周期 ID 的闩锁全部失效 → T1 连续减仓。上一轮加的三道防线只是保险丝，不是修复。 |
| 3 | **五条保护链没有仲裁** | 交易所 STOP、T1/T2/T3 结构减仓、黑天鹅市价全平、抄底专属止损（死代码）、TP 后利润保护，同一时刻可能三条同时判，优先级只体现在 `if` 的先后顺序。 |
| 4 | **请求量靠熔断兜底** | 每仓每 5 秒 `_find_stop_orders(force=True)` + `_position_fresh(force=True)` 绕过所有缓存，44 个方向 ≈ 17 req/s。于是需要 429 退避、418 冷却、熔断、自适应休眠一堆补丁。 |
| 5 | **减仓预算不统一** | T1 20% + T2 30% + TP1 20% + TP2 30% = 100%，TP3 还要再减，语义上已超支，只靠 `min(current_contracts, ...)` 挡住。 |
| 6 | **死字段拉活数据** | `entry_classification` / `t3_waived` / `bottom_fish_sl` 从未被赋值，但 `entry_classification_lookback_bars=500` 还在为它们多拉 500 根 K 线。 |

## 2. 新架构：三层，职责单一

```
                    ┌──────────────────────────────────────────┐
                    │ runner.py  —— 调度（单循环，不按仓位开协程）│
                    │ 批量拉仓位/ticker → 生命周期确认 → 并发执行 │
                    └───────────────┬──────────────────────────┘
                                    │ 仓位快照 + 风险周期状态
                    ┌───────────────▼──────────────────────────┐
                    │ risk_model.py —— 决策（纯函数，可单测/回放）│
                    │ 快照 → 动作列表（reduce / exit / stop）    │
                    └───────────────┬──────────────────────────┘
                                    │ 动作
                    ┌───────────────▼──────────────────────────┐
                    │ ledger.py —— 状态（一仓一行 + 审计事件）    │
                    │ protection_positions / protection_events  │
                    └──────────────────────────────────────────┘
                                    │
                        engine.py 的下单原语（复用，不改）
              maker 循环减仓 / 市价兜底 / 算法单兼容 / 双源价格校验
```

三条硬规则：

1. **决策是纯函数**：`decide(state, snapshot, conf)` 不碰网络、不碰数据库，同样的输入必然同样的输出。参数调整先用历史 K 线回放，再上线上。
2. **状态一仓一行**：写 `BTC|long` 只影响这一行，物理上不可能覆盖 `ETH|long`。
3. **交易所 STOP 只兜底**：正常情况由内部四档先动作，STOP 放在灾难线之外 1.5 ATR，只负责「引擎死了/断网了」的极端情况，避免和内部逻辑抢着平仓。

## 3. 决策模型

### 3.1 四档减仓：结构定位置，ATR 定缓冲

多单（空单镜像）：

```
entry ────────────────────────────────
  │  T1 = 7 根低点  − 0.5×ATR   减 15%   ← 实时价 + 持续 30s 确认
  │  T2 = 26 根低点 − 0.6×ATR   减 20%   ← 实时价 + 持续 45s 确认
  │  T3 = 83 根低点 − 0.8×ATR   减 25%   ← 实时价 + 持续 60s 确认
  │  T4 = 83 根低点 − 1.5×ATR   减 40%   ← 立即（全平档）
  ▼
disaster = T4 − 1.5×ATR   交易所 STOP 兜底（只在引擎失效时成交）
```

- **T1 被夹在 `[1.5%, 8%]` 之间**：结构位贴着开仓价时至少退到 1.5%，避免被噪声扫掉；结构位太远时最多 8%，单笔风险不会失控。
- **四档强制单调**：每档之间至少间隔 `0.8×ATR`，不会挤在一起变成「一次破位连减四次」。
- **持续确认而不是收盘确认**：v1 的 T2/T3 要等 2h K 线收盘，最坏情况破位后 2 小时才动作。v2 用「实时价 + 持续 N 秒」，插针不算，真破位 30~60 秒内就动。
- **跳空穿透多档**：如果一根线直接穿过 T1+T2，不是分两次减，而是按累计比例（35%）下**一张**单，减少滑点和请求。

### 3.2 优先级（每轮只出一个减仓动作）

```
1. 击穿灾难线   → 全平（不确认、不等收盘）
2. 击穿结构档位 → 累计减仓（实时价 + 持续确认）
3. 到达止盈档位 → 累计止盈
4. 止损上移     → 独立计算，永远重算，只许朝盈利方向移动
```

### 3.3 止盈与让利润奔跑

| 档位 | 触发 | 减仓 | 说明 |
|---|---|---|---|
| TP1 | 1R | 25% | 同时把 STOP 推到保本上方 |
| TP2 | 2R | 30% | STOP 推到 TP1 上方锁利 |
| TP3 | 3R | 30% | STOP 推到 TP2 上方 |
| 余仓 | — | 15% | 交给 `峰值 − 2.5×ATR` 追踪止损 |

R 的定义：**R = |开仓价 − T1|**。R 来自结构而不是固定百分比，所以不同波动率的币用同一套参数也成立。

保本：浮盈到 **0.5R** 就把 STOP 推到 `entry ± 0.2%`（你选的胜率优先）。

### 3.4 止损阶梯

交易所 STOP 的候选价取以下最大值（多单），且绝不放宽：

1. 灾难线（初始）
2. 浮盈 ≥ 0.5R → 保本价
3. TP1 完成 → 保本价；TP2 完成 → TP1 上方 0.1%
4. 每减一档 → 推进到下一档结构线（**减仓与敞口同步收紧**）
5. 浮盈 ≥ 1R → `峰值 − 2.5×ATR`

只有推进幅度超过 `max(0.15% × 价格, 0.15×ATR)` 才真正去交易所撤单重挂，避免每轮抖动。

### 3.5 默认参数

| 参数 | 默认 | 含义 |
|---|---|---|
| `tier_ratios` | `[0.15, 0.20, 0.25, 0.40]` | 四档减仓比例，合计 100% |
| `tier_confirm_sec` | `[30, 45, 60, 0]` | 每档持续确认秒数，0=立即 |
| `tier_atr_buffer` | `0.5` | 结构位外侧的 ATR 缓冲 |
| `tier_min_gap_atr` | `0.8` | 档间最小间距（ATR 倍数） |
| `risk_min_pct` / `risk_max_pct` | `0.015` / `0.08` | R 的夹取区间 |
| `disaster_atr_buffer` | `1.5` | 交易所 STOP 在灾难线外多远 |
| `tp_r_multiples` / `tp_ratios` | `[1,2,3]` / `[.25,.30,.30]` | 止盈档位与比例 |
| `breakeven_trigger_r` | `0.5` | 保本触发 R |
| `trailing_start_r` / `trailing_atr_mult` | `1.0` / `2.5` | 追踪止损启动点与回撤幅度 |
| `v2_poll_interval_sec` | `3` | 巡检间隔 |
| `action_retry_cooldown_sec` | `90` | 同一动作失败后的重试冷却 |

## 4. 与 v1 的行为对照

| 维度 | v1 | v2 |
|---|---|---|
| 调度 | 一仓一协程，44 协程各拉数据 | 单循环批量拉，决策协程池并发 4 |
| 状态 | 全表 blob，跨币种覆盖 | 一仓一行，物理隔离 |
| 周期识别 | `openTime`/均价变化即换周期 | 只在**加仓**或**开仓时间变化**时换周期 |
| 减仓触发 | T1 实时 / T2-T3 等收盘 | 全部实时 + 持续确认，跳空合并成一张单 |
| 减仓预算 | 各分支独立写死 | 统一按「占初始仓位比例」记账，合计 100% |
| 交易所 STOP | 结构止损，与内部减仓抢跑 | 只兜底（灾难线外 1.5 ATR） |
| 止盈后 | STOP 抬到保本/TP1 | 同样，另加 ATR 追踪让余仓跑 |
| 请求量 | 每仓每 5s 两次 force 请求 | 全市场 ticker 1 次/轮，K 线 30s 缓存，挂单 10s 缓存 |
| 可观测 | 只有日志 | 每个动作写 `protection_events`，前端「最近保护动作」可见 |
| 可回滚 | — | `engine_version=v1` 立即回退 |

## 5. 灰度与回滚

1. **先演练**：`dry_run=true` 跑 1~2 天。引擎照常判断、写事件、写日志，但**不下单**。打开保护页能看到「本应执行什么」。
2. **再小仓验证**：`dry_run=false`，用 1~2 个小仓位观察 24 小时。
3. **全量**：确认无异动后放开。
4. **回滚**：保护页「风控引擎版本」选 `v1`，或直接 `POST /api/protection/config {"engine_version":"v1"}`，引擎 5 秒内切换，账本数据保留（回 v2 时可继续用）。

部署：服务器 `cd /root/trading_webapp && ./deploy.sh`。

---

## 6. 已知边界

- **没有样本外验证**：四档参数是结构+ATR 的常规做法，但没有用历史数据做参数寻优。建议上线两周后用实盘事件表（`protection_events`）回看「每档触发后的最大有利/不利偏移」，再调比例。
- **止损与减仓可能同时发生**：极端跳空时，交易所 STOP 与 T4 减仓可能同时触发；两者都是 `reduceOnly`，最终仓位正确，但可能多一次废单。可接受。
- **币安以外的交易所**：算法单兼容层（`algo_compat.py`）沿用 v1，未做新增适配。
- **`protection_state` 旧表**：切到 v2 后不再写入，数据保留不动，回滚 v1 时可继续读。

## 7. 测试

`backend/tests/test_protection_v2.py`（21 条，全离线）：

- 计划构建：多/空四档单调、R 的双向夹取、比例归一化；
- 决策：持续确认、回到线内清零、跳空合并、灾难全平优先、预算不超 100%；
- 止盈：TP1/TP2 顺序、跳空保留 15% 余仓；
- 止损：0.5R 保本、只升不降、减档后推进、不会落到价格错误一侧；
- 周期识别：减仓不换周期、加仓换周期、停机期间重开换周期；
- 账本：一仓一行互不覆盖、事件倒序与按币过滤。
